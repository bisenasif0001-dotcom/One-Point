# Step 15: local expansion and handover

Local expansion preserves the desktop brand. It does not constitute a live launch or business approval of every task.

302 static action links across 27 service-family pages now open a short service request instead of an unavailable or scope-dependent checkout. Education tasks retain their exact selected name, including competitive exams, admissions, scholarships, university assistance and academic services. The request page asks the team to confirm availability, documents and the complete price. It creates no order, collects no applicant data, and sends nothing automatically. WhatsApp opens only when the customer chooses it.

Shared dynamically generated service actions resolve an existing catalog identity before opening checkout. Unknown tasks and starting-price work request confirmation. PAN keeps its six-task selector. MSME and verified visiting-card packs retain their direct ordering flow. Custom print designs use a quote request rather than the unverified shape/material/finish calculation as a payable price. No catalog price, eligibility exception or document waiver was invented.

Expanded family pages have mobile-specific compact heroes, single-column education cards and usable wrapping actions. Changes are restricted to mobile; existing desktop appearance and detail content remain. The request screen renders task names as text, including hostile query values, and uses an explicit WhatsApp link.

## Validation and maintenance

Run `npm run test:expansion` for the family-page viewport matrix and request identity/escaping checks. Its local browser blocks external requests. Run the existing direct-entry checks after editing shared routing. Reports under artifacts distinguish browser checks from real-phone or provider checks.

After adding a supported task, configure its exact catalog ID, pricing model, authoritative amount and required documents together. Export catalog/policies, review duplicate-ID conflicts and deliberately restore the corresponding request entry to exact checkout only after a family-specific booking test. Do not map a detailed task to a vaguely similar parent service. For custom print products, define server-validated configuration pricing before enabling fixed checkout. The current request links remain conservative until those rules are approved.

The entry expansion script is a migration aid, not an automatic recurring catalog synchronizer. Do not treat a zero unresolved-link report as proof of fulfilment support: request-only tasks remain available for enquiry rather than verified online payment.

Rebuild the local release after changes with `npm run release:build`, then `npm run release:verify`. Use deployment/PILOT-RELEASE.md, ROLLBACK.md and MONITORING.md for later deployment and maintenance. Never upload transaction backend files or private runtime data to public Pages hosting.

## Remaining full-version gates

Real Android/iPhone keyboard, camera and payment-app switching; trusted HTTPS backend configuration; provider sandbox/payment verification; staging backup/restore rehearsal; live post-deployment smoke checks and monitoring remain pending. Catalog conflicts and request-only services need operator-approved policies before online purchase expansion. The user will deploy later; no live changes were made. Local implementation and automated checks are not proof that every physical device or every service can accept payment.
